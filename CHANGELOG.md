# Changelog

What has changed, per release, written for someone deciding whether to download
this rather than for someone reviewing the diff.

Entries land under `## [Unreleased]` as work happens. Cutting a release moves
that section into a dated one of its own and empties the queue, and the same
text becomes the body of the GitHub release — so the notes are written by
whoever did the work, not reconstructed afterwards from commit subjects.

Headings are fixed; `scripts/changelog.py categories` prints the list, and
`scripts/changelog.py check` rejects anything else. Empty headings are dropped
when the notes are rendered, so leaving one at `_Nothing yet._` costs nothing.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and
the version numbers follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
While the major version is 0, a minor bump is where behaviour is allowed to
change; see [`docs/RELEASING.md`](docs/RELEASING.md).

## [Unreleased]

### Reconstruction
- **Creatures walk the patrol routes their level authors gave them.** A quarter of the disc's placed creatures — 174 of 651, 9 of BASE1's 22 — name a path corner in their spawn record, and this port had never spawned a corner or installed the resolver that finds one. The console has a dedicated spawner at `0x8007F390`, reached from `0x80057588` where the literal `"PathCorner"` picks the group out by name: it allocates through `0x8005F848`, which stamps class byte 114 and raises the in-use bit, writes the record's `+0x10` into `entity+0x18` as the corner's own targetname and `+0x14` into `entity+0x16` as the next corner's, and copies the origin VERBATIM — no eye lift, no thirty-unit nudge and no drop to the floor, all of which a creature record gets. `monster_start_go` (`0x80061BA4`) then resolves the creature's target with G_PickTarget (`0x8005F708`), sees class 114 at `0x80061C10`, turns the creature at the corner and calls its walk handler; with no resolver every lookup failed and it took the other arm instead — target cleared, pause set to forever, stand. BASE1 zone 1, 600 headless frames: `creatures.moved` 0 before, 5 of the 8 live creatures patrolling after. Corners are kept in their own array rather than in the monster set, because `set.count` is the denominator the mission HUD divides kills by and `class_module[]` is indexed by the Population class 0..37, where 114 belongs to the other class namespace entirely.
- ...and they walk the whole route, not just to the first corner. `path_corner_touch` (`0x8005F1F8`) hands the creature the corner after this one, the pause the record's `+0x0E` byte asks for, or the never-expiring stand when the chain ends. It is reached from G_TouchTriggers (`0x8005F4A8`) at `0x8005F598` as a SPECIAL CASE on the class byte rather than through a touch pointer, which is why the spawner installs none; the port's step already had the touch hook the original calls from `SV_movestep` (`0x80060300`) and nothing had ever installed it.
- The path record's `+0x10`/`+0x14` were written down here as "link0/link1 neighbour index (INFERRED)". `0x8007F3E0`..`0x8007F3F4` say they are targetname and target, and read that way BASE1's twenty corners form closed cycles — 25 to 28 to 27 to 26 to 25 — that eight of that map's nine creature links land on. `+0x0C` turns out to be the same nine-bit spawn-flag transport a creature record uses and `+0x0E` is the corner's wait. The creature entity filler (`0x8007E5A0`..`0x8007E6DC`) never writes `entity+0x18` at all, so on this disc a targetname belongs to a path corner and to nothing else.
- **Rotating hatches open, wait and swing shut again.** `ROTHATCH` runs a seven-state machine off the jump table at `0x800ABDA0` and this port ran one state of it, so every one of the disc's seventeen hatches turned the instant its script reached it and froze at its target for the rest of the level. The other six are here: state 5 counts `item+16 * 300` down before anything moves and only then lifts the box and plays `pt1__strt` (`0x8002B2F8`, `0x8002B3C8` - the port had been playing it on the trigger, a second early on BASE2's and WASTE1's delayed hatches); state 2 holds open for good when `item+17` is zero (`0x8002B2D0`); state 6 counts `item+17 * 300` down, refuses to count `0xFF` at all, and reloads itself with ONE while the calls keep coming, which is what holds a hatch open under a standing player (`0x8002B3F0`); state 3 sweeps back with the same `(speed*dt)/8` subtracted and finishes on the `0x800`/`0xC00` quadrant flip rather than a sign test, so the negative-speed hatches close correctly too (`0x8002B578`). The timers are loaded by the exec on a trigger and only while the hatch is idle (`0x8002DDF8`), so re-triggering one mid-hold no longer extends it. MATRIX4 zone 0 with `--fire-triggers`: `world.hatches_open` is 2 through frame 240 and 0 by frame 300 - both hatches have swung shut - where before they stood open for ever. Only the visual half is restored: the console's box lift at `0x8002B3B4`/`0x8002B5F8` has nothing to move, because no rotator in this port reaches the collision world.
- ...and that trigger is a per-frame flag, not a latch. `0x8002B270` reads bit 24 of `obj+0x50` and clears it from the object before dispatching, in every state; the port kept a sticky `running`, so a script calling `ROTHATCH` every tick at an already-open hatch nudged it one step past its target and snapped it back, replaying `pt1__end` each time. SECURITY's two never-closing hatches drop from 74 counted tick-moves to 43 on a 1200-frame run, which is that jitter going away. The arrival sound is now raised only on the positive-speed arm, because `0x8002B54C` - the arm a hatch whose target is at or past 2048 takes - sets state 2 and jumps straight to the loop stop with no play call in between.
- **A creature's claw misses when you are out of reach.** `fire_hit` (import +0xEC, `0x80061118`) is the only thing a melee frame calls, and its first act is a range test: it builds `enemy->origin - self->origin`, calls VectorLength (`0x80061188`), and at `0x80061198` `slt v1, aim[0], range` jumps to the epilogue at `0x800614B4` returning FALSE — no damage, no hit point, nothing. The port ran none of it, so every swing connected from any distance: the AI commits to melee at 1020 but the swing resolves two or three 10 Hz frames later, and a player who backs off in between was still being clubbed. The reach is the raw origin-to-origin distance (the mins/maxs work at `0x800611A4` runs after the gate and only shapes the hit point) and the comparison is strict, so `range == 1020` still lands. Headless on the PAL disc, `--demo --watch --frames 1800`: WASTE1 refuses 2 of 8 swings, JAIL3 1 of 24, both counted in the new `report.creatures.swings_short`.
- **A creature's shotgun throws five pellets, not twelve.** `monster_fire_shotgun` (+0x88, `0x80061ED0`) reads a0..a3 and nothing else — its only stack access is `lhu s1, 112(sp)`, the trace's cell hint — and loops on its own constant at `0x80061FD4` `slti v0, s0, 5`. The twelve the Soldier's module passes, and its 1000/500 of spread, are never read. The port was delivering all twelve at 2 points apiece, so a shotgun guard's blast did 24 where the console's does at most 10. Headless, SECURITY, `--demo --watch`: the player was dead by frame 250 (health -16, then -68 at 300 and -120 at 350) and now finishes those same three runs at 60, 48 and 24.
- **Every level ran without its opening script.** The zone loader runs the named event `STARTLEV` at every level and zone load — `0x8007C290` materialises the twelve bytes at `0x800AD558` ("STARTLEV", NUL-padded) and `0x8007C324 jal 0x80027CC4` runs it, bracketed by the initial-state flag at `0x8007C2AC`/`0x8007C338` — and this port ran it on no map at all. 18 of the 49 COMMON scripts carry one, and walking their TRIGGER closures they DISABLE 22 records on eight maps and raise 13 TIMEDLIGHTs, 8 TIMERs, 2 SIMROT2s, a LIFT1, a PLATFORM and a MISEVENT. LAB shuts twelve records at load, eleven of them behind trigger volumes the player walks through, so five doors, two button-and-lift pairs, a CREBATCH ambush and a message all worked from frame 0 and a progression gate opened before the progression. The pass is not gated on the zone carry and comes before the EVE_ replay, as `0x80079114` comes before `0x80079130`, so a zone seam re-closes what it closed: LAB now reports twelve records disabled on each of its five zone loads, and 400 headless frames on LAB run 188 script calls where they used to run 562.
- **A repeating TIMER is a window, not a continuation.** `0x80026FEC` claims one of the eight 20-byte slots at `0x800C6F74` and fills it with the record, a FIRE COUNT from item+8, an ITEM WINDOW from item+10, the TIMER item itself and a resume pointer; the sweep at `0x80027340` runs `slot+6` items and no more (`0x800271F0`), wraps past the TIMER item when it runs off the end (`0x8002721C`..`0x80027240`), stores the resume pointer back (`0x80027270`) and re-arms unless the fire count has reached zero — a count of 0 being clamped back to 0 at `0x800273EC`, so 0 is forever. This port read neither operand and ran the whole remainder once. 13 of the disc's 18 TIMERs diverged: BOSS2's flicker loop fired all eight of its TIMEDLIGHTs together and stopped, and BOSS1's arena destruct detonated six groups on one deadline where the console stages two every second, eleven times. The slot is keyed on the TIMER item (`0x8002703C`..`0x80027054`), which is what stops a CAT_B record under the player's feet from eating the table, and a full table drops the request rather than evicting (`0x80027084`). BOSS1's `Flash` — base 2, fires 1000, window 2 — used to add two script calls to a run of any length; it now adds 34 over 200 headless frames and 100 over 600, one every 0.2 s.
- The re-arm's fresh `rand()` roll (`0x800273F0`) is the one thing not reproduced: the roll belongs to the owner's CALL hook, which is not running at a deadline, so the period armed by the first roll is reused. Every TIMER on the disc carries range 0, so the console's re-roll returns that same constant and nothing here can tell them apart.
- **Every blast pushed half as hard as it should.** The impulse scale is read out of the BLAST FORCE global on every hit -- `0x80057F84 lh 0x800B3358`, then `125 * (v + 64) >> 6` for an ordinary hit and `25 * (v + 64) >> 2` when a player hurt themselves -- and unlike GRAVITY and GAME SPEED nothing transforms it on the way in: `xrefs 0x800B3358` finds the reset that writes 64 (`0x80020498`), the menu slider's store (`0x8001BE38`) and that one read, and nothing else. The port had the arithmetic and the field, and no writer: the BLAST FORCE row on four menu pages set a value nothing consumed, so the scale was 125 and 400 where the disc's are 250 and 800. Forty-eight points of rocket now push a target 1280 units where they pushed 640, and a deathmatch run that rocket-jumps around SECURITY ends 565 units further along Z and 344 higher than it used to.
- **The BFG's beams do damage.** `0x80049B9C` is called from the ball's think every tick and does two things to each target that clears its filters: refreshes a 45-tick green beam AND hurts it, 10 points in single player (`0x80049E28`) or 5 in deathmatch (`0x80049E10`), throttled by the halfword at ball+0x4C so it lands about ten times a second. The port had transcribed only the beam, so the lattice was decoration and the weapon was worth its contact hit plus one 1300-radius blast; a Soldier the ball sailed past took nothing. The filters are here too, and two of them were missing entirely: the owner is skipped (`0x80049C54`), anything past 3072 units is rejected on squared origin distance (`0x80049CA4 lui v0, 0x90`), and the visibility test at `0x80049CE0` -- which this file had described in a comment and never performed, so beams were held through walls -- now gates both halves. Ten scripted BFG shots on SECURITY kill two creatures where they killed one.
- **A shot player flinches.** `0x8003A1C8` builds one animation id for the live player and `0x8003AE08 addiu s5, zero, 3` sets it to PAIN unconditionally whenever the damage byte at entity+0xDF is non-zero, outranking STAND, RUN, JUMP and ATTACK; `0x8003AE0C` clears the byte, so it asks once per hit, and the death arm at `0x8003ADB8` returns before the read, so a killing tick never asks. The port had reconstructed the chooser `0x8003CE14` complete with its PAIN arm (`0x8003CF74`, `rand() % 3` over Pain 1/2/3) and the rule that a pain move holds until it wraps (`0x8003D188`), and then asked it for nothing but DEATH -- the client picked ATTAK/JUMP/RUN/STAND by four `return`s of its own and had no pain case at all, so Male2's three flinches were unreachable. The request now goes through the transcribed chooser, sourced from the damage byte rather than from a health diff (a recorded hit that took nothing off either bar still flinches), and the clip holds for its full span instead of being cut off by the next tick's STAND.
- **A frame that ends somewhere the player may not be is thrown away.** Every arm of the stepped mover `0x8004583C` converges on a validity gate at `0x80045D54` that the port had no counterpart for at all: it fetches the entity's own sweep mask (`0x8005553C`, flag bit 0 -> `0x810` or 0), asks `0x80050CE0` with `a2 = 0` — the entity's LIVE box, not the swept envelope the per-move retry at `0x8004576C` uses — and `a3 = !ON_ENTITY`, and on a hit at `0x80045D80` discards the whole lift/slide/drop, restoring `entity+0xA2` and `+0x54..+0x5C` from the pre-lift snapshot taken at `0x80045A98` (`0x80045E04`). Only if that passes does it re-locate the cell with `find_node(pos, hint, brute = 0)` and store it (`0x80045DB4`). This is the last-resort guard against a closing door, a descending crusher or a lift leaving a player embedded in it: the sweeps cannot help, because a mover that arrives around a stationary player was never in the path of anything the player's own moves swept. The repo had already noticed the hole from the other side — `monster.h` names `0x80045C54`, `0x80045C90` and `0x80045E14` as the three stores to `entity+0x54` inside that function, and only the first two were reproduced. `0x80045E14` is this rewind. A frame ending inside a mover's box now leaves the player at the 500 it started the tick at instead of the 800 the step carried it to, and 400-frame headless runs on SECURITY, BASE0, BASE1 and QFRONT report the gate reached on every one of their 609/388/606/608 ticks, re-locating the cell every time and rewinding none of them — the guard is silent in ordinary play, which is what a last-resort guard should be, and every reported position is unchanged to the unit.
- The second chance the gate gives a position no cell claims (`0x800447C0`) is approximated rather than transcribed. Its `bgez a2` head accepts a NEGATIVE cell index outright and the port reproduces that — without it an entity with no cached cell would be rewound every tick and frozen — but the `>= 0` path's plane walk with slack and centroid retry is replaced by the strict `q2_coll_point_in_node` (`0x80044098`), so the port is stricter than retail here. `report.player.gate_unplaced` counts every time that difference could matter; it is 0 across all four maps above.
- **A weapon pickup puts the gun in your hands.** Walking over a shotgun added the shells, drew the caption and its icon, and left the blaster up: the only thing that ever changed the held weapon was working the carousel by hand, and firing did not rescue it either. The console's weapon-give helper `0x80037E28` does two stores — `0x80037E7C` raises the owned bit in client+104, and `0x80037E84` puts the weapon just taken into client+102 when client+98, the weapon whose model is raised, is the blaster. The port had only the first: the second was written into `q2_inventory.current_weapon`, a byte with no reader in the running game, while the live weapon sits a layer up in `sim.combat.weapon_id`. The item sweep now REPORTS the grant and the sim performs the switch, keyed by the sweep's player slot so a parked split-screen player's pickup cannot move player one's gun. On BASE0 at the first Shotgun P (-1091,-89,3519), `--headless --frames 40 --report` goes from `report.player.weapon 1` to `report.player.weapon 2`, and the view-weapon log from `Blaster G` throughout to `Shotgun G` on the frame it is collected. Holding the railgun instead, it stays 10 — `0x80037E78` is blaster-only.
- ...and the gate that decides it now reads the weapon you are holding. Because `current_weapon` was written by the pickup path and by nothing else, the console's blaster-only test was being made against a stale shadow: take a shotgun, cycle back to the blaster with the pad, walk over a railgun, and the disc switches while the port did not. The byte stays — it is the console's own zero-based record and it is in the save format — but it is no longer what anything decides on.
- **WEAPON STAY does something.** In deathmatch with the row switched on, a gun is supposed to stay standing for the other players instead of vanishing under the first one to touch it. `0x800B3360` is that setting, and it is a halfword of its own rather than a bit of the GAME VARIABLES word at `0x800B29EC`: the page's row table points straight at it (`0x8009A748`), `0x8001BE5C` and `0x800204B4` clear it, and it is read with `lh` in two places — `0x80037E60`, where a weapon already held is refused, and `0x8005988C`, where a weapon-style pickup is kept in the world. Both were transcribed; neither could run, because `q2_entity_world.weapons_stay` had two readers and no writer anywhere in the tree. It is carried from the menu now, ungated by the session type the way the console carries it, and both readers test deathmatch themselves.
- **Monsters are solid.** A creature and a player could walk through each other, and the console makes them solid in a place this port had not reconstructed at all: two instructions at the top of the stepped mover `0x8004583C`, which appends the entity to the frame's actor list (`0x80045990`) and then runs a separation pass over it (`0x80045998`). That pass walks the 32-slot list at `0x800B2B90`, rejects on a six-face box overlap, tests a HORIZONTAL cylinder of `entity+0x90` — a constant 128, not the 286 at `+0x94` a shot uses — and adds `dx * pen / dist` and `dz * pen / dist` into the entity's own frame delta at `+0xEC`/`+0xF0`, so the push is swept through the world with the rest of the motion and a body is never shoved into geometry. Both movers reach that one function, so one pass makes every body solid to every other in both directions. Dropped exactly on a Soldier on SECURITY, the player is now separated to 256 units — the two radii — and stays put 400 units away.
- The creature half of the same thing uses the sweep's OWN radius, and the two are different fields: `0x800545F4` is `lh a0, 64(a2)` with `a2 = entity+84`, which is `+0x94` and is 286 for a player, while the separation pass's `0x80051428` is `lh v1, 144(a1)`, which is `+0x90` and is 128. 286 is the player's own half-extent, so a creature that stops 286 from a player's centre stops at their skin. The narrow phase itself is combat.c's, shared rather than written twice — `q2_combat_cylinder_interval` — because the shot path and the movement clip differ only in their filter.
- The creature half of the same thing: `0x8005BD3C` clips a step trace against the world hull, then the door boxes, and then, gated on the caller's `0x02000000` mask bit, sweeps the actor list (`0x8005BF4C jal 0x800544EC`) with the walker's own entity as the one to ignore. `SV_movestep` passes `MASK_MONSTERSOLID` on every step, so a creature is stopped by the player and by other creatures. The port's binding dropped `ignore` on the floor with a note saying it had no per-creature box list; it has one now, and a 600-frame run on SECURITY reports 143 of 1845 step traces cut short by a body.
- The stand-on arm of the separation pass is deliberately NOT reproduced. `0x80051454` compares the other body's top against `20(sp)`, and the function's only stack stores are its register saves and its own box — `20(sp)` is never written. The comparand is uninitialised stack, so with anything address-shaped in it the console falls through to the push arm and what the arm would otherwise do is not determinable from the image.
- Split-screen local play now accepts independent SDL gamepads: keyboard/mouse plus three controllers by default, or four controllers with `--gamepad-player-one`. Short button taps survive high frame rates, hotplug keeps the other players' assignments stable, and each player can change weapons and request their own respawn.
- Versus now plays successive rounds, preserves wins between arena reloads and finishes at the round limit. Results latch each player's READY response and wait the retail 150-tick interval after everyone agrees before returning to multiplayer setup.
- Creatures drop what they carried. A creature whose spawn record carries the drop flag now leaves an item when it dies: `monster_death_use` queues it in the console's four-slot queue (`0x80020D60`), the frame drains it through the 30-row pick table at `0x800AB79C` (`0x80020680`), and the item is thrown from the body's own origin with the console's toss and lands before it becomes a pickup (`0x8002085C`, `0x80020C48`). A scripted firefight on SECURITY asks for six drops and all six land. Nothing had ever called any of it, so every creature on the disc died empty-handed.
- Gibs. A body taken past its gib threshold comes apart as it does on the console: a blood spray laid over its posed mesh (`0x8005B320`), then a ring of tumbling chunks thrown along the killing hit's push (`0x8005A3D4`, `0x8005A0AC`), each trailing blood until it lands (`0x80059DE0`). Before, a Soldier hit by a rocket played an ordinary death.
- Damage shows on the body. An energy hit crackles across a creature's posed mesh, the other damage timers throw sparks off it, and a player under quad damage wears the blue shell — the five hooks of `0x8005B880`, drawn through the third particle spawner (`0x8002FDFC`, absolute world points) and a posed world-vertex lookup (`0x8006CC44`) the port did not have. A corpse carrying one of the two lingering effects dissolves and is freed rather than sparking on (`0x8005B2A8`).
- Each creature sees from its own eye and turns at its own rate: a walker from its model's height — a Soldier at -252, a Tank Commander at -508 — a flyer at -250 and a swimmer at -100, turning 228 or 114 a tick where every creature had turned 200 (`0x80062448`..`0x80062584`). A prone Insane is a flyer for its whole life.
- Event scripts run once when they say once. A one-shot item retires itself before it dispatches (`0x80027468`) — BASE2's end-of-unit call drops from twenty runs to one on an in-out-in walk — a record's one-shot is its DISABLED bit, so an ENABLE genuinely re-arms it (`0x80027950`); opcode `0x09` WAIT is live (`0x800276C4`); an accepted zone gate abandons the rest of its record (`0x80027784`); and a trigger volume must have its enable bit set and its id match the player's cell (`0x80027E64`), a gate checked against every event volume on the disc before it was switched on.
- Crossing a zone boundary inside a map keeps the level's script state. The console carries every record's and item's latch across a same-map zone change and replays the spent ones with seven settling passes (`0x8002936C`, `0x800296D4`..`0x8002974C`), so a door a script opened arrives open and a one-shot batch, message or secret does not happen twice. The port had been re-arming the whole script at every seam.
- The status bar is the console's. The ammo counter reads the pool the weapon fires — the rocket launcher showed 200 where it holds 50, and the BFG showed 0 — the selected weapon is drawn in the centre slot the port never had (`0x80037CAC`), the previous and next weapons sit either side at their true left edges, faded away from the centre and drawn as the console draws them, an additive icon over a subtractive shadow; health goes negative, to -99; every field draws at the console's 1.5x brightness; split screen gets its own numeral size; and a dead one-player bar strips back to health and the gun (`0x80033C68`).
- The loading screen is read, and it turns out to be two things the disc keeps apart. The word is the executable's: `0x80079178` — the first act of every level transition — opens menu page 46 and installs `0x800A3314`, one record reading `{ "LOADING", 256, 124 }`, followed by a NULL one that leaves the page pure text and so keeps the selection bar off it. The load itself is deferred to a one-shot hook, which is why the console's screen is a single frame frozen for as long as the disc takes. `docs/FORMATS.md` §11.13.
- The logo turning beside that word is a **sprite strip, not a model**, and it was in the file this project has been reading the menu's letterforms out of since the font was found. Rows 144..203 of `frontend.lbm` hold a 23-cell rotation of the Quake II logo on a 32 x 20 grid, with `RETRY` in the twenty-fourth slot. The cell widths — `17 16 14 13 11 9 7 5 4 5 7 9 11 13 14 16 18 19 19 21 22 22 22` — narrow to one minimum and out again, which is |cos| and is a rotation, and every cell is the full 20 rows tall, which is what turning about a vertical axis looks like. That explains its colour (the menu font's own palette, so it is the pale blue the word is), its size, and how an in-level load can show a logo at all: `frontend.lbm` is in every playable map and no model of the logo is.
- **Two earlier answers here were wrong and are retracted.** The first said the picture comes from `LEVELS/QDUMMY/`, whose whole contents are one model (`Q2LOGO`), one image and an empty zone; a retail capture showed the logo hollow, which rules a solid model out. The second reached for `q2logowire`, QFRONT's outlined twin of the same mesh — right shape, wrong colour, and in the one directory an in-level load cannot borrow from. Both were models because the title screen's logo is a model. What survives is the observation about QDUMMY's shape, not the argument from it.
- The front end's own version of the screen, from the same capture: `0x80101E4C` — the handler all three difficulty records call — builds module page 19, whose records are `STARTING` at (256, 111) and `GAME` at (256, 137). A third page in the module is one row reading `DEMO OF GAME` and belongs to the attract loop. Those two rows are also the ruler the logo's corner was measured with, being the only things in the capture whose frame-buffer coordinates are known. `docs/FORMATS.md` §11.13.1.
- **The North American disc plays.** `Quake II (USA)`, `SLUS-00757`, is catalogued by the hash of its executable, and that executable turns out to be the PAL one linked again: 158,097 of PAL's 158,208 words find a partner in nine runs of constant displacement, so the port carries those runs and reads every table in it by PAL's documented address. Before this the disc ran with no menu, HUD, weapon, effects, music or creatures, because every table refused an unknown build. The disc also ships the linker's own symbol table, and it names what this project had identified by address — `T_Damage`, `M_CheckAttack`, `PrimaryQuakePlayer`, `ProcessLensFlares` — every one of them right. [`docs/FORMATS.md`](docs/FORMATS.md) §9.13 lists everything NTSC changes, and there is not much of it.
- **The blaster and the hyperblaster had each other's bolt.** The spawner every bolt goes through (`0x8004D70C`) takes a flags halfword as its fifth argument and a means of death as its sixth — `lhu s1, 128(sp)` at `0x8004D714` into `record+0x22` at `0x8004D7BC`, and `record+0x32` at `0x8004D7B0` — and it has exactly three callers: the player blaster passes (11, 6) at `0x8004C11C`/`0x8004C124`, the player hyperblaster (14, 5) at `0x8004D3E8`/`0x8004D3F0`, and `monster_fire_blaster` passes one pair or the other on `andi v0, 104(sp), 0x40` at `0x800620A8`. Five bits of that halfword are each a separate arm of the per-tick sweep: `0x1` the particle trail (`0x800482B4`), `0x2` the dynamic light (`0x800481C4`), `0x4` the eight-corner box (`0x80047F44`, and `0x8004D7A4` deciding whether to write the corners at all), `0x8` the impact burst (`0x8004862C`), and `0x10` a second, wider light that no caller sets — `xrefs 0x80048AFC` returns one allocator caller, so that arm is dead on this disc rather than merely unused. 11 and 14 differ in bits `0x1` and `0x4` and nowhere else, so the blaster is a trail with no body and the hyperblaster a body with no trail; they are mutually exclusive, and this port drew a body for both and a trail for neither.
- **A blaster bolt trails six particles, once a tick.** The bit-`0x1` arm at `0x800482BC`..`0x8004858C` is a group spawn through `0x8003004C`, whose six call sites this port had none of. It builds the segment the bolt just swept — `start = pos - delta/2` (`0x80048328` `sra 17`, `0x80048334`), `offs[0] = -delta/2`, `offs[i] = offs[i-1] + (delta<<4)/6` (`0x80048384` `sra 12`, then `div` by `record+0x4A`, a hard 6 from `0x8004D7A0`), `vel[0] = delta>>4` and `vel[i] = delta>>4 + ((rand() - 16384) >> 12)` — and asks for 6 particles, life 23, size 8192 and ramp `0x8009BF04` at both ends. `delta` is the sweep's own `vel * dt` (`0x80047D50`), truncated to a halfword by `sh v1, 136(sp)`, so the port converts the bolt's velocity back to the raw units the spawner stored it in. It runs once a tick and not more: `record+0x42` increments and then clamps to `record+0x3A`, which the spawner sets to a hard 1 (`0x8004D7B4`).
- **The blaster's means of death was the BFG's.** `weapon.c` had both energy rows on `Q2_MOD_ENERGY_BOLT` = 1, which `0x80049E34` and `0x8004BC48` show belongs to the BFG's beam and contact. The consequence was not cosmetic: `q2_mod_effect_timer` (`0x800585A4`..`0x80058604`) arms one of four bytes on mods 1, 2, 4 and 5, so every blaster bolt was lighting the green energy effect on whatever it hit and the hyperblaster, whose mod really is 5, was arming nothing. The flags are not saved, because the three call sites pair them one for one with the mod — 11 always with 6, 14 always with 5 — so a restore reconstructs them from what is saved.
- **A crate you shoot open runs the rest of its script, and on BASE0 that is where the jacket armour comes from.** Destroying a `func_explosive` is two different events on this console depending on what killed it. The exec `0x800267C4` returns 0 while the group stands (`0x80026834`) and `item + 28` once the destruction loop has run (`0x800269FC`), and the weapon-impact router tests exactly that at `0x8002EFA8`: on a non-zero answer it reads the record offset out of `obj+0x40`, adds the item own length to get the NEXT item, and hands the record back to the executor `0x80027950`, which walks to that item and runs what follows. The script route does not — `0x800276B0` returns 0 and the record the item is already inside carries on by itself — so only a SHOT continues the record. BASE0 COMMON.DAT record +508 is [FXGROUP item+512 hp 10, CALL CREBATCH "Amour", CALL INSECRET], the batch "Amour" holds exactly one place record — id 4 Jacket P at (-15402,-52,-4731), inside that group own box — and nothing else on the map can reach record +508: its TrigBounds name seventeen other offsets, its Events directory holds only ALWAYS and CRATES, and its single list opcode names record 160. Shooting the crate now reports `CREBATCH 'Amour' woke 0, placed 1` and `secret found: 1 of 4`, where before it reported the crate breaking and nothing else. Ten records across the disc have a tail behind a shootable `0x08` item and six of them, BASE0 included, are reachable no other way — WASTE2 is a Large Medi Pack in "ExploBox", LAB rec+1868 is a shootable button that opens a door and prints a string, SECURITY rec+2364 arms a list. The shootable door leaf `0x8002F050` has the same contract (`0x8002F144` / `0x8002F148` return `item + 24`) and is carried through the same way.
- **The shotgun cocks.** `wep_shotgr1b` is sound-table entry 5 and it had exactly one reader in the image that this port had not transcribed. `0x8004C460` `sb s4, 695(s5)` raises a byte on the player entity on every shotgun shot that fires; the view weapon per-substep driver spends it at `0x80050484`..`0x800504D0` — the weapon must be id 2, the byte must be up, and `0x800739B8` must report that the handle at `entity+276/278`, the voice `wep_shotgf1b` was started on, has stopped sounding. While the bang is still playing `0x800504B4` drops the request and asks again next substep; the first one after it finishes plays the cock and `0x800504CC` clears the byte. So it lands about half a second after the shot — the sample is 12,936 frames at 22,050 Hz, 0.536 s once the console 35/32 pitch is applied — and, because a second shot restarts the voice and re-raises the byte, after the LAST shot of a burst rather than between shots. The port `anim_step` begins at `0x800504D4`, the jump table over weapons 3/6/7/8/11; the twenty-one instructions before it were never carried across. It is the plain shotgun alone: `0x8004C488`..`0x8004C740` contains no write to +695, and `wep_sshotr1b` is the FALLBACK NAME for the same slot at `0x8004DC38`, not a second sound. 600 headless frames holding fire: 4 shots, 4 cocks; the super shotgun and the machinegun raise none.

### Client
- **The end-of-match banner is on the screen now, not only in the log.** A match or a VERSUS round ended, the arena kept rendering for a second and a half, and then the scoreboard appeared: the player never saw TIME UP, GAME OVER, ROUND OVER or ROUND DRAWN, and never saw who won. All three of `q2_mp_banner`, `q2_mp_find_winner` and `q2_mp_winner_text` were being called, and all three only inside a `Q2_INFO`. QMULTI.C's per-frame hook picks one of four one-item tables by end state (module+0x1518/+0x1548/+0x1578/+0x15A8, each `{ text, 256, 124 }`), enters page 45 at `0x80100FD8`, loads the winner row into item slot 16 (module+0x14E8, `{ "", 256, 20 }`, filled by `0x8010098C`) and the banner into slot 32, and ticks the page until its own countdown at module+0x15DC passes zero. So the winner line is at the TOP of the screen and the banner across the middle, not stacked, and a drawn round shows the banner alone (`0x80101008`). A `--dm-frags 1 --dm-stage --demo` run on MATRIX5 now reports `match.banner_frames 44` between the frag limit and the request for MPResults, where it reported nothing and the capture in that window was bare.
- **The MULTIPLAYER page's `□ RULES` prompt does something.** QFRONT has been sliding that caption up at y = 220 whenever the cursor stood on DEATHMATCH, TEAM DEATHMATCH or VERSUS, and pressing SQUARE did nothing at all — the port's menu engine tested TRIANGLE and CROSS and no other button. The module's own hook runs the two off one predicate: `module+0x4630` computes `cursor - first < 3`, raises the prompt, and then `module+0x4654` reads the SQUARE bit out of the just-pressed word at `engine+0x2BC` and calls `module+0x4868`, which indexes the six-entry jump table at `module+0x11C4` with the mode it wrote into `engine+0x370` and installs that mode's banner and rules table. All six tables are now transcribed — `module+0x0F434` DEATHMATCH, `+0x0F4DC` TEAM DEATHMATCH, `+0x0F59C` CAPTURE THE FLAG, `+0x0F68C` TAG, `+0x0F734` TEAM TAG, `+0x0F824` VERSUS — keyed on the mode rather than on the row, because the mode is what the console indexes with. Three of them are NINE records, not the eight `menu pages QFRONT` shows: that reader caps a page at `q2_lb_menu_row row[8]`, so VERSUS used to stop at "POINT. THE FIRST PLAYER TO" with "REACH SCORE LIMIT WINS." (`module+0x0F8E4`, at 256, 196) left in the image, and CAPTURE THE FLAG and TEAM TAG lost their last lines the same way. Every page installs the empty table at `module+0x0FADC` behind its own, so nothing on it takes a cursor or a selection bar, and its back handler is the MULTIPLAYER builder, so TRIANGLE returns.
- **HORIZONTAL SPLIT is reachable again, and the front end says VIBRATE.** The title screen's OPTIONS pages were being served the *executable's* in-game tables, and two of QFRONT's differ. Its VIDEO page (`module+0x0EEF4`, installed by `module+0xCC0C`) is the three-row one — HORIZONTAL SPLIT at 98, SCREEN POSITION at 124, RESET TO DEFAULTS at 150 — and it is the module's only video table, so the front end offers the split whether or not a match is running; the port served the two-row single-player table instead, 13 pixels high and with the row missing. That mattered more than a missing row usually does, because `Q2_SET_HORIZONTAL_SPLIT` is read once, at match start, so the front end is the only place a player can set it: a two-player match was always horizontal unless `--split` said otherwise. Its CONTROLLER page (`module+0x0FA4C`, `module+0x39D8`) abbreviates four of its five labels — VIBRATE, SWAP Y, MOUSE where the executable says VIBRATION, SWAP Y AXIS, USE MOUSE — and it does have the MOUSE SPEED slider at `module+0x0FAAC`, which `menu pages QFRONT` hides because the module-page reader drops any record whose x is not 256.
- **The loading screen no longer appears at the end of a zone.** It was raised for every load — a level change, a restart, a save being restored, the front end's own arrival — and the executable says it belongs to one thing: `xrefs 0x800A3314` finds the `{"LOADING", 256, 124}` record materialised by ONE instruction in the image, inside `0x80079178`, and `xrefs 0x80079178` finds exactly two callers, the ZONEGATE opcode handler (`0x80027828`) and the TELEPORT primitive's exec (`0x80028ACC`). Both are zone changes inside one map. A level change is state 2 and a unit end is state 7 and neither goes near it, so the port was inserting a black half second at every level boundary and two of them at every unit end — one between the tally board and the end-of-mission placard and one after it.
- The word LOADING is white. `0x80079398` writes 1 into drawable 0's `+0x48` — the highlight flag — immediately after `0x80079364` enters page 46, and the port had that observation written down in `loading.h` and in `pages.c` and acted on it in neither: the page's only row is index 0 and its cursor is 1, so nothing was ever selected and the word came out in the sheet's blue. Measured off a capture of a real zone gate it was (64, 128, 160). It draws through palette 70 now, on the same band every highlighted drawable gets.
- Every loading screen restarts the logo. `q2_loading_raise` restarted the hold and left the strip where the last screen stopped, so the second screen of a session opened a third of the way through the rotation and the third opened a third further on — against the whole reason the strip is walked backwards, which is that the screen should open on the logo facing the player. The console cannot have the fault: `0x80079364` enters page 46 and re-installs both records from scratch at every transition.
- A load that finds nothing takes the screen back down. It was raised before the read and never lowered when the read failed, so asking for a zone a map does not have was half a second of LOADING over a level that had not gone anywhere.
- **A zone change was reading freed memory.** `q2_creature_world` borrows COMMON.DAT's `Population` chunk, and every load re-reads COMMON — including a gate between two zones of one map. Between the swap and the creature reload sits `q2_sim_settle`, which ticks the world, which runs CREBATCH, which walks that chunk. AddressSanitizer on `--map JAIL3 --zone-probe`: heap-use-after-free, twelve bytes read in `q2_pop_get_group`. It crashed four runs in five; the fifth read whatever the allocator had put back and carried on.
- `--report` prints the run's own counters at exit, one `report.<group>.<name> <integer>` per line — frames, ticks, loads, loading screens, the player's position and health, creature census and step traces, movers, script calls. A scripted run's only verdict used to be its exit code.
- ...and that exit code now means something: `main` returned 0 whatever happened, so `--map NOSUCHMAP` and `--movie TYPO` were indistinguishable from a level that loaded and played.
- The loading screen is back between levels: black, LOADING in the menu's own face, and the Quake II logo turning in the top right — the disc's own 23-cell strip, at the rate the front end turns the model it was rendered from. Every load raises it — a level change, a zone gate, a restart, a save being restored, the front end's own arrival — and nothing under it ticks while it is up. Loads here are effectively free, so it is held for half a second: a floor in real time, not a frame count, so it is the same half second at 30 Hz and at 144. The load that STARTS a run is exempt — `--map` puts you in a level rather than at a doorway, and every capture this project takes is `--frames N --shot`, which would otherwise photograph the loading screen.
- And the half second between confirming a difficulty and the opening reel is `STARTING` / `GAME` over the same black, which is what the console shows. This port drew a blank front end for those fifteen frames.
- The strip is walked BACKWARDS, so the screen opens on the logo facing the player. Half a second at a cell every 22 ticks is about seven of the twenty-three cells, so which end those seven come from is most of what the rotation ever is: forwards it opens at a width of 17 out of a 4..22 range and is edge-on before the screen goes; backwards it opens broadside and turns away, which is what the capture shows. Like the palette, this is measured off a picture rather than read — nothing found binds this quad, let alone counts its index.
- The logo is GREY and the word is not. It is drawn through the executable's built-in palette 4 — `000000 080808 181818 ... D8D8D8 E8E8E8`, a monotonic sixteen-step grey ramp. The strip is authored against palette 68, a blue ramp of sixteen entries in the same index order, so 4 is the same picture with the colour taken out: same weight, same anti-aliasing, no blue. Nothing else in the bank is: 75 is that ramp stopped at 0x78 and comes out too dark, 76 runs bright-to-dark and inverts the art, 73 is flat white, and 70 — the white-only mask, four live levels out of sixteen — leaves a stippled fragment. Which palette the console binds is not read: the strip is data with no located reader, so this is measured off a capture the way the corner and the size are.
- The intermission boards no longer spend their welcome behind the loading screen. The tally board had the same hole.
- On the USA disc the game is the NTSC one: a 512 × 240 screen at 60 Hz fields, a world that steps 10 of the console's 1/300 s units a frame instead of 12, films at their own 30 fps and cut where the NTSC modules cut them, logo screens and music timed in 60 Hz fields, menus four lines higher on the shorter screen (except the memory card's SAVE FILE page, which NTSC left alone), and the four-player split in NTSC's own 119-line quadrants.
- American English where the USA build has it. ### Rendering and audio
- **Finding a secret is no longer silent.** Every secret in the game gave the on-screen line and nothing else; the console chimes. INSECRET's exec loads the handle at gp+16884 (`0x80028F98`) and plays it at the triggering entity's feet (`0x80028F9C`, `a1 = s2 + 84`), and that handle has exactly one writer in the image — `0x8002DA50`, storing what `0x80073518` returned for the name at `0x800ABCB0`, `msc_secret`. It is in thirty of the disc's forty-nine sound banks: every single-player level, none of the thirteen arenas or six menu banks, none of which carries an INSECRET call. Both the text and the sound sit inside `0x80028F80`'s branch, so a map whose `FoundASecret` key does not resolve still gets neither, while the counter past the join runs either way. SECURITY reports `level.secret_sounds 2` against `secrets_found 2`; it read nothing at all.
- **The quad's firing sound stopped stacking.** `itm_damage3` is 1.05 s long once the 35/32 pitch is applied and a spinning machinegun or hyperblaster asks for it at the spin threshold's hard 10 Hz, so ten copies of one sample played in phase with each other; even a blaster at 2.5 shots a second stacked three. All four of the console's quad-fire sites share one voice handle at `0x800B2B80` and throw the request away when `0x800739B8` says it is still sounding (`0x8004FBA4`..`0x8004FBB0`); only an idle handle reaches the play at `0x8004FBC4`, which writes the new handle back. The port's mixer had no way to ask, so it now carries the console's own answer: `0x80073734` stores a (slot, tag) pair and `0x800739E4` and `0x80073924` both bounds-check the slot against 24 — the same 24 voices this port has — and compare the tag, which is why a recycled slot cannot be mistaken for the sound that was started. 300 headless frames of held chaingun fire on BASE2 raise the sound 92 times; with a device attached, 53 of 59 raises are now refused. The sound also goes through the item table's own key (slot 9) rather than a literal, so a bank substitution reaches it like the other ten item sounds.
- **A rotating hatch has a motor again.** It thudded once as it started, turned in silence and thudded on arrival. `pt1__mid` has exactly one reader on the whole disc — `0x8002B3DC`, inside ROTHATCH's handler, in the same basic block as `pt1__strt` — and `0x8002B568` hands the handle back to `0x8007398C` on arrival, immediately after `pt1__end`. The port had decoded, named and wired all of it and deliberately not raised it, because the mixer could start a looping voice and not stop one; it can stop one now, with the tag guard above. The motor is a channel of its own rather than a third value of `sound_pending`, because a hatch that finishes its travel in a single tick — BASE3 and MAGDEMO each have one — raises the start and the arrival between two drains, and the console plays both. `world.rot_loop_starts` and `world.rot_loop_stops` both read 1 on those two maps and balance; they read 0.
- **Every effect the game spawns was being culled before it reached the screen.** A particle group is filed under an area and the group draw drops one whose area has no screen-change record to drain — which is right, and which no sim-spawned burst could survive, because every gameplay spawn site passed a literal 0 and no collision cell on the disc carries area 0 (`q2psx-inspect coll`: contents != 0 on 22,767 of 22,773 nodes). So a bullet left no smoke puff, a rocket no fireball, a hit no blood, a damaged creature no crackle and a pickup no burst, in every zone with an authored SortData stream — the default and the great majority. The console resolves the byte instead: the third spawner runs `0x800686C4` on its area argument (`0x8002FED0`), which returns a non-zero argument as is and otherwise looks the point up in PrimaryColl and takes the cell's byte +32 (`0x80068710`), and the hitscan's own site forwards the TRACE's area record, `lbu s1, 32(v1)` at `0x80048854`. Both are reproduced at the call sites — the trace already ran, so the bullet path costs nothing extra — and the per-actor chain and the pickup burst resolve theirs from the point. BASE1 zone 0, 400 headless frames with `--god --shoot`: `report.fx.prims` 0 before, 27,900 after.
- **The integrator ran before the draw, so a one-tick effect was never drawn at all.** On the console the integrator IS the tail of the draw — `0x800304A8` draws every group and only then, from `0x80030B1C`, reads each life, skips a zero one and writes it back one lower — so a burst raised during the frame is shown at its full life and stepped afterwards. This port spawns and integrates in the sim tick and draws from the client, which aged every burst before any frame could show it: the quad-damage shell and the energy-bolt crackle are life 1 and both re-spawned every tick, so neither had ever appeared, and every other burst opened one ramp entry down its fade and lived a tick short. A group now carries one tick's reprieve from its spawn, which is exactly the tick the console spends drawing it. Same run: 26,100 primitives without it, 27,900 with.
- **A shattered pane threw twenty-one invisible chunks.** Debris pieces moved, bounced and expired correctly and nothing ever drew one, because nothing ever registered a model: the console fills a 32-slot list at `0x800D56B0` through `0x80064F70` and the burst picks from it uniformly (`0x80064748`), and this port's registration function had no caller at all, so every piece took the no-model arm. The client now registers the map bank's `Debris1`..`Debris3` **by name** at zone load — index would be wrong, since only 19 of the disc's 49 banks carry them and Debris1 sits at 19 on LAB and POWER2, 2 on SECURITY, 25 on WASTE1 and 20 on WASTE3, where POWER2's index 0 is `BFGBlast` — and the live pool is drawn beside the projectiles, each piece turned by `RotMatrix(entity+0xE6)` rather than through the instance's yaw path, which negates the middle angle. A map that carries no Debris model still registers nothing and still throws unmodelled pieces, which is the console's answer on the other 30. BASE1 zone 0 with the GLASS pane shot out: `report.fx.debris_models` 3, `report.fx.debris_faces` 1,058, both 0 before.
- **A creature hit by an energy weapon never took the colour.** `0x8005B880` opens by calling the ambient fade `0x80075E14` with a step count of 7 (`0x8005B88C`, `0x8005B894`), which walks the body's own back colour at `entity+0x2AC` a seventh of the way toward its target per tick, and the `effect[1] >= 3` arm copies the energy preset at `0x800AEAAC` straight into that field (`0x800586E8`) — so a bolt turns the body green for a tick and it eases back out. The port had reconstructed the fade and never called it, wrote the report's ambient flag and never read it, and fed the creature and player-body draws a hardcoded `0x30` triplet instead. All three are wired now. The fade's compare is signed (`slt v0, v1, a1` at `0x80075E38`), so green falls to the target in one call while red and blue climb by 48 / 7 = 6 a tick; the target itself is the port's own `0x30` and says so, because nothing found writes a creature's `+0x2B0` after its spawn.
- **The BFG's beam trail was culled by the same area gate as the particles.** The timed beam list is re-submitted into the transient pool every frame, and the port submitted each record with a literal area of 0 — which the beam draw culls exactly as it culls a group. The console resolves the owner's own area on every submit: `0x80048D24` runs the point-clip helper `0x8004E920` over the record's owner and `0x80048D50` `lh a3, 64(sp)` hands its answer to the beam queue as the area argument. The port now resolves it from the ball's position on each refresh and stores it on the record, so a BFG in flight draws the lattice it leaves behind instead of only lighting the room.
- **Bolts, sparks and beams were projected through a camera of their own.** A blaster bolt left the gun and hung in mid-air below and to the left of the barrel with nothing joining it to the muzzle; impact sparks and blood sat off the surface they were spawned on; and none of it leaned when the view rolled. There is only ONE camera per frame on the console and every emitter installs it: `0x8003058C` is `SetRotMatrix(view + 160)` in the effect draw and `0x80047CA4` is the same call in the projectile draw, and view+160 is the matrix `0x80037F38` builds by handing the basis at view+192 and the viewport's `(vw, vh)` to `0x80055DE4` — which scales row 0 by `vw/320` and row 1 by `vh/240` and copies row 2, giving `diag(1, 2/3, 1)`, the anamorphic camera the world draw loads at `0x800313CC`. A scan of the whole text segment finds a direct `ctc2 R11R12` in game code at exactly one address, `0x800313DC`, so there is no second camera for the emitters to use. The port's effect emitter built a plain yaw/pitch basis of its own — no anamorphic term and no roll — and the projectile emitter installed nothing at all, projecting with whatever the effect pass had left behind. Everything they drew was pulled towards the crosshair by a third of its distance from it: at the BASE0 spawn, `--headless --map BASE0 --shoot --frames 30 --shot-every 3`, the frame-12 bolt's centroid moves from x 307.5 to 333.4, which is `256 + 1.5 * (307.5 - 256) = 333.25` — the whole missing factor — while its y is unchanged at 162, because row 1 was never wrong. The near test and the quad-size divide read only row 2, which neither the scale nor the roll touches, so nothing else moved.
- Split-screen HUD digits and icons now use the multiplayer atlases at their authored size. Health, ammo, armour and frag counts no longer shrink twice or lose their edge pixels.
- Crosshairs, notifications and damage flashes belong to each player's viewport. Crosshairs no longer sit in the split-screen gutter, and one player's underwater effect no longer warps everybody's view.
- Each split-screen player now has their own view weapon, animation, firing, recoil and lighting. Death removes only that player's gun, respawn rebuilds it, and the extra views follow their owner's standing or crouched eye height.
- Split screen: a particle group's per-viewport skip tested the wrong bit, so nothing marked as one player's own was ever hidden from the others (`0x80030614`).
- ...and `--boot` gets the same silence. The hold was armed beside one of the two places `boot_chain` is set, and `--boot` sets the other one while the arguments are still being read — so a run that asked for the logo screens explicitly still played the menu track over them. It is armed where the chain's own condition is decided now, so the two cannot drift.
- The menu music no longer plays over the startup screens. On the console the boot chain is three levels — QLOGOS2, QLOGOS and QFMV — and none of the three has a playlist, so the legal screen, the two logo pairs and the intro film are scored by the film's own audio and nothing else. This port loads QFRONT before the chain so the front end has something to stand on when the film ends, and that load was taking QFRONT's looping menu track with it. The music now starts where the console's does: when the title screen is actually up.
- **A bolt is an opaque box that shades orange to yellow, not an additive quad in the light's colour.** `0x80048160` hands the eight projected corners to `0x800B1E28` with the face table at `0x8009D664`, and that emitter writes a nine-word, 36-byte packet — `ori t0, zero, 0x9`, `sb t0, 3(a3)`, `addiu a3, a3, 36` — carrying four per-vertex colours and no UVs. Nine words with four colours is POLY_G4: gouraud and untextured, and the command byte on all twenty-four colour words is `0x38`, the opaque code. ### Fixes
- **Every gun-carrying creature fired up to ten times too often.** `M_CheckAttack`'s post-shot reload is `level.time + random() * 20` TICKS: `0x8005DC50`..`0x8005DC58` build `rand()*5*4`, `0x8005DC5C`..`0x8005DC7C` divide by 32767 with the 0x80010003 magic-number sequence, and `0x8005DC88` stores the sum into `entity+0x110`. That is up to two seconds on the ten-Hz clock. The port had the multiplier left at id's seconds value of 2, so the cooldown was 0 to 0.2 s and a Soldier could fire again on the AI tick after the one it fired on. SECURITY zone 2, 3000 headless frames with `--god`: 132 creature shots before, 83 with this one constant corrected.
- **The breadcrumb trail's head pointed at the newest crumb instead of the oldest.** `PlayerTrail_Add` (`0x80060A70`) writes AT the head — `0x80060AEC` loads it, `0x80060B04`/`0x80060B14`/`0x80060B24`/`0x80060B38` store into that slot — and only afterwards, at `0x80060B88`..`0x80060BA4`, reloads it, adds one and masks with 7. So the head names the slot about to be OVERWRITTEN, which is the oldest, and that is where PickFirst's scan starts (`0x80060BF4`). PlayerTrail_LastSpot (`0x80060FFC`) says the same thing from the other side: the most recent crumb is `trail[(head - 1) & 7]`. This port advanced first and wrote at the new head, so both picks always answered the crumb the player had dropped a third of a second ago and a creature that lost you walked straight at where you are now, through geometry, instead of following the route you took. The crumb's stored yaw goes with it: `0x80060B3C`..`0x80060B80` subtract the PREVIOUS crumb's origin and hand that to vectoyaw, so it is the direction the player was travelling and not the way they were looking. And the `valid` byte the port had added is gone — PlayerTrail_Init (`0x80060F20`) memsets all eight twenty-byte slots and raises the active flag, so an unvisited slot is a crumb at the world origin with timestamp 0 and the scan walks past it on timestamp alone, where the guard made pick_next answer nothing where the original answers a stale spot.
- A crumb is laid when the player can no longer SEE the previous one, not on a timer. PlayerTrail_Add's only caller (`0x8007E32C`) first asks for the last spot at `0x8007E2C4`, tests it with `visible` at `0x8007E2D0`, and at `0x8007E2D8` skips the add when it is still in sight. That is what makes eight slots span a whole route: they are corner markers. Dropping one unconditionally every ten frames made them 2.7 seconds of dense samples, so even a correctly ordered trail only ever led a creature back along the last few strides.
- **The crumbs were recorded at the player's eye and consumed as entity origins.** ai_run's arrival test is `dist*dist >= |pos - last_sighting|²` with `dist` one frame's step — about 144 to 230 for a Soldier's run frames — and a crumb in the eye frame carries a constant `Q2_VIEW_STAND - Q2_EYE_BASE` = 290 in Y. 290² is 84100, so the waypoint could never be reached, `AI_PURSUE_NEXT` was never raised again and the pursuit pressed against its first crumb for the whole 25-second search. The same frame of the client hands the AI tick a player ORIGIN forty lines further down, with a comment explaining the rule; the trail was the one consumer that had never been converted with it.
- **A creature that heard gunfire opened fire immediately.** PlayerNoise stamps the noise entity with the level clock — `0x80062CC8` loads `level.time` from `0x800E46DC` and `0x80062CD4` writes it to `+0xD0` — and `ai_checkattack`'s AI_SOUND_TARGET arm measures staleness against exactly that stamp. Nothing in this tree had ever written the field, so from level time 51 onward the comparison was always true, the flag was dropped on the creature's very first check, and the investigate behaviour it gates — walk toward the noise, stop and look around inside 768 units, hold fire for five seconds — never ran for even one tick.
- **A locked door now says which key it wants.** The refusal arm plays `msc_keytry` and then calls `0x800254EC` with the door's own mask (`0x80025870`), which switches it onto one of eleven names, formats `You need the %s` (`0x800ABBF8`) and puts the sentence on the CENTRE line through `0x80043570` -> `0x80042E14`. The port made the noise and printed nothing: `q2_hud_need_key` existed, had no caller anywhere in `src/`, and formatted into the notification ring - `0x80042D4C`, a different entry - rather than the centre line. The port had the test outside the direction split, on the reading that the `16` at `0x80025D08` is loaded on both arms - it is, but that instruction is in the obstruction handler at `0x80025CBC` and says nothing about where the decrement runs. The group spans [newpos - disp, newpos], the segment just travelled; raised first it spanned the segment travelled on the PREVIOUS tick, leaving a whole step of clear air between a bolt and the streak behind it.

### Rendering and audio
- A software rasteriser built to the PlayStation's rules rather than filtered to look like them: exact fixed-point GTE with its saturation flags and reciprocal table, affine texture mapping, ordering-table sort with no depth buffer, 15-bit RGB555 with the ordered dither, all four semi-transparency modes, texture pages, CLUTs and the mask bit. Every one is individually toggleable, so the same build runs perspective-correct at 4K.
- Models draw textured, animated, lit through the GTE's own three-light gather, and backface-rejected against the model linker's own NCLIP pair.
- Lens flares, the water warp, the damage flash, and the status bar with the icon and caption for what you just picked up.
- Audio: SPU-ADPCM sound bank playback for the menu, items, player and every creature; and each map's own seven-track XA playlist.

### Tools
- `q2psx-inspect` identifies a disc, verifies every level file against the documented schema, and checks every format claim in the docs against the disc — so "we understand this format" is something the build evaluates rather than something a document asserts. It also renders levels, models, HUDs and menus to a PPM with no window, and carries a PS-X EXE loader and an R3000A disassembler for the questions only the executable can answer.
- `stx2avi` demuxes a film into the raw video and audio streams ffmpeg can mux, driving the same decoder the game uses rather than a second one.

### Fixes
- The repository could not be cloned on Windows at all. A tracked file was called `nul.ppm`, and `NUL` is a DOS device name, so Git refuses to create it: the *checkout* failed, not the build. Renamed to `parity-frame.ppm`, content unchanged, and `scripts/check_paths.py` now fails CI on any tracked path Windows cannot create.
- Nothing had ever built on Linux. The link failed on undefined `sin` and `sqrt` because nothing asked for libm, which glibc keeps in a library of its own where Windows and macOS fold it into the C runtime.
- `disc.c` did not compile under GCC either. `fseeko`, `ftello`, `off_t` and `strtok_r` are POSIX rather than C11, and this project compiles as strict C11, under which glibc hides them — and an implicitly declared `strtok_r` would have truncated its returned pointer to 32 bits on a 64-bit host. A CD image can exceed what C11's `long`-based `fseek` reaches, so the POSIX interfaces are declared rather than given up.

### Build and packaging
- The version lives in one file, `VERSION`, which CMake reads to seed `project()` and the generated `version.h`. A binary, a tag and an archive cannot disagree about what was built.
- A manual release workflow builds Windows, Linux and macOS, tests each, and only then tags and publishes — so a tag never points at a commit that does not compile. `scripts/` holds the version, changelog, release-note and packaging tools it runs, each usable by hand.
- CI builds and tests on GCC, Clang, MSVC and Apple Clang with warnings as errors, and checks that the version each binary reports is the one in `VERSION`.
- A fetched SDL3 never shipped in the Linux or macOS archives, so those would have contained a client that could not start. Shared libraries now build beside the executables and the client carries an `$ORIGIN` rpath.
